# AI戦略司令室 運用ルール — 2026-09-27 23:35

## A. 基本原則

- ChatGPTチャットは作業セッションであり、唯一の正式記録ではない。
- Git / GitHub / プロジェクト内ファイルを正式な状態・履歴として扱う。
- GitHub上の正式記録と実repo状態が矛盾する場合、確認できた実状態を優先し、差異を明示する。
- 不明な情報を推測して正式状態として記録しない。
- 重要な変更は人間承認を挟む。
- 作業範囲を明示する。
- 「ここだけ変更」は文字どおり厳格に守る。
- 可能な限り可逆性を保つ。
- Local / GitHub / 引継ぎ資料に差異がある場合、いきなり同期せず差分を確認する。
- AIの自律性を活かすが、重要な境界は人間が保持する。

## B. 正式記録

AI戦略司令室の横断正式記録は、当面 `yoshioide2301-dev/DrivingSchoolApp` の `docs/ai-strategy-room/` に置く。

主要ファイル：
- `AI戦略司令室_引継ぎ_YYYYMMDD[_HHMM].md`
- `AI戦略司令室_運用ルール_YYYYMMDD[_HHMM].md`

旧ファイルは履歴として残す。既存正式記録の削除・大幅変更は人間承認を必要とする。将来的なAI戦略司令室専用repo化は改善候補とするが、現時点では実施しない。

## C. ChatGPTの責任

複数PJ横断整理、情報整理、要件定義、設計、比較・分析、調査、方針提案、引継ぎ情報整理、Claude Code用指示作成、Claude Code結果レビュー、GitHub正式記録の直接読み込み、整合性確認、次作業設計。

実行していない操作を実行済みと表現しない。確認していないGitHub状態を確認済みと表現しない。

## D. Claude Codeの責任

ローカルrepo確認、ファイル作成・編集、実装、テスト、Git status / diff、環境調査、承認後のGit操作。

Claude Codeは引継ぎそのものには必須ではない。ChatGPTがGitHub上の正式引継ぎファイルを直接読める場合、通常のチャット引継ぎではClaude Codeを中継しない。

## E. 人間の責任

目的、優先順位、重要設計判断、高影響操作の承認、不可逆操作の承認、commit / push / 公開 / 本番反映の承認、実機確認、最終判断。

# F. 3自己更新ループ

## F-1. IMPROVE

目的：作業結果から継続的に改善する。

対象：品質、速度、UI/UX、コスト、プロンプト、AI連携、開発手順、PJ運営。

改善案は提案できるが、重要ルールをAI自身が勝手に正式変更しない。

## F-2. DEFEND

目的：新しい危険・権限・事故要因を検出する。

対象：AIモデル、Claude Code、ChatGPT、Plugins、MCP、GitHub、Actions、Agent、Secrets、認証、外部入力、自動化。

重大な問題では安全を優先し、人間へ通知する。AI自身がセキュリティ境界を勝手に弱めない。

## F-3. ALIGN

目的：AI・Local・GitHub・正式記録の状態不一致を検出する。

確認対象：PROJECT、CWD、REPO、branch、HEAD、remote、git status、未commit変更、GitHub、引継ぎ資料。

特に重要作業開始時、チャット引継ぎ時、repo移行時、sync前、pull前、merge / rebase前、重大な実装後に実施する。

ズレを発見した場合、**同期より先に差分確認**を行う。

# G. PROJECT / CWD / REPO

Claude Codeへ重要作業を依頼する前に、PROJECT / CWD / REPO の三点一致を確認する。異なる場合は実装を開始せず、対象repoを確認する。

## H-1. AUTO
安全な通常作業は可能な限り自律実行させる。過剰な承認要求で開発速度を落とさない。

## H-2. HUMAN ASK
git add / commit / push / pull / fetch / merge / rebase / reset / checkout / switch、GitHub write operations、package install、npx、Claude security settings編集等の重要操作は人間確認を要求する。User-level ASKがauto modeを上書きすることは実機確認済み。

## H-3. GLOBAL DENY
Claude credentials、SSH private key、.env実Secrets、private/signing key、GitHub token表示、repository deletion、force push、hard reset、destructive clean等を拒否する。

## H-4. Bypass禁止
`disableBypassPermissionsMode = "disable"` を維持する。

## H-5. Security settings変更
Claude自身に自分のsecurity boundaryを自由に変更させない。セキュリティ設定変更は、設計 → 検証 → 人間承認 → 人間適用または明示承認された適用 → read-only再検証を基本とする。

# I. GitHub Security

GitHub CLIの不要な `delete_repo` scopeは削除済み。現在の基本scope：repo / gist / read:org。Git protocolはSSH。repository削除権限等、通常開発に不要な強権限を追加しない。main branch protection / rulesetは推奨follow-upとして扱う。

# J. Secrets

Secrets本文をChatGPT、Claude chat、docs、source code、logs、commits、screenshots、正式引継ぎ資料へ出力・保存しない。

対象例：API key、access token、password、private key、credentials、.env、Apple signing secrets。

必要な確認は、存在・ファイル名・scope・masked value等で行う。

# K. Git操作

- `git add .` を通常運用で使わない
- `git add -A` を通常運用で使わない
- explicit staging
- commit前にgit status / diff確認
- push前にcommit内容確認
- push後にGitHub確認
- 未commit変更を勝手に消さない
- reset / restore / stash / discardを勝手に行わない
- blind pull禁止
- blind sync禁止
- force push原則禁止
- merge / rebase前に未commit変更を確認
- LocalがGitHubより遅れている場合、先に差分確認

# L. Claude Code識別形式

Claude Codeへの重要指示は原則、
`【PROJECT: XXXXX】`
`【TASK: XXXXX】`
から開始する。Claude Codeの結果にも可能な限りPROJECT / TASKを含める。

# M. 標準実行フロー

1. ChatGPTが目的・範囲を整理
2. PROJECT / CWD / REPO確認
3. 必要に応じてClaude Codeへ指示
4. Claudeが実装・検証
5. Claudeが変更内容・git status等を報告
6. ChatGPTがレビュー
7. 人間が重要操作を承認
8. commit / push等
9. GitHub反映確認
10. 必要なら正式記録更新

# N. チャット引継ぎ

現チャットで現在状態・決定事項・未決事項・次作業を整理し、必要な情報をGitHub上の正式引継ぎファイルへ保存する。

新チャットではGitHub上の正式ファイルを直接読み込む。チャット履歴やAI記憶だけで正式状態を補完しない。

確認：正しいrepoか、正しいpathか、最新引継ぎか、GitHub実状態との矛盾がないか、次作業は何か。

新チャットで引継ぎ成功を確認するまでは旧チャットを保持し、確認後は原則 `【過去版】` へリネームする。

# O. ファイルアップロード抑制

引継ぎ目的で同じファイルをChatGPTへ再アップロードする運用を原則避ける。GitHub上の正式記録を直接読む。ただし通常資料・画像・PDF等は必要に応じてアップロードする。

# P. DEV環境標準

Windows上のactive development repoは、将来的に原則 `C:\Users\yoshi\Development\` 配下へ整理する。

例：Development\ZeroNavi / Development\MICHITO / Development\GCP / Development\ZGF-Website。

Desktopを恒久的なrepo置場としない。開発repoのroot名を「Claude」としない。repoはAIツールの所有物ではなくユーザーの開発資産である。

# Q. Repo移行

repo移行は原則 `COPY → VERIFY → NEW PATH TEST → OLD PATH RETIRE` とする。Explorer等による即MOVEを標準にしない。

VERIFY対象：.git、branch、HEAD、remote、tracked、untracked、ignored、git status、important hashes、Claude trust、permissions、PROJECT / CWD / REPO。

旧repoは新環境の安定確認前に削除しない。

# R. UI/UXファースト

UI/UXが製品価値の中心となるPJでは、機能実装より早い段階で、最終画面像、情報階層、視覚的優先順位、操作フロー、タップ領域、状態表示、実機確認を行う。

「実装できる」だけでなく、「ユーザーが使いたい」「次に何をすればよいか分かる」ことを重視する。

# S. 人間承認が必要な代表操作

重要な設計変更、重要コード変更、security boundary変更、commit、push、公開、本番反映、reset、restore、stash、discard、force push、repository削除、正式記録削除、重要な認証・権限変更、旧repo削除。

# T. AI参謀長システムの開発原則

巨大な管理システムを先に作らない。

ZeroNavi、MICHITO、WeatherAnalysis、ZGF HP等の実PJを進め、その過程で実際に価値が確認できた仕組みだけをAI参謀長システムへ追加する。管理すること自体を目的化しない。

現在の自己更新ループは、IMPROVE / DEFEND / ALIGN の3本を基本とする。新しいループは、既存3ループで扱えない明確な問題が発生した場合だけ追加を検討する。

# U. 最終原則

AI戦略司令室の目的は、**AIの能力を最大限活用しながら、正式状態・安全境界・重要判断を人間が保持し、実プロジェクトを速く正確に前進させること。**

速度だけでも、安全だけでも、管理だけでもない。改善・防御・整合性を保ちながら、実際の成果物を完成・公開・収益化へ進める。
