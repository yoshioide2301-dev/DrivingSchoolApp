# AI戦略司令室 運用ルール — 2026-09-27

## A. 基本原則
- チャットは作業場（作業セッション）であり、唯一の正式記録ではない。
- Git / GitHub / プロジェクト内ファイルを正式な状態・履歴として扱う。
- GitHub上の正式記録と実際のリポジトリ状態に矛盾がある場合は、実際のGit/GitHub状態を優先し、差異を明示する。
- 重要な変更は人間の承認を挟む。
- 不明な情報は推測しない。
- 作業範囲を明示し、「ここだけ変更」は文字どおり厳格に守る。
- 変更は可能な限り可逆性を保つ。

## B. ChatGPTの責任範囲
ChatGPTは主に以下を担当する。
- 情報整理
- 要件定義
- 設計
- 比較・分析
- 引き継ぎ情報の整理・更新案の作成
- Claude Codeへの指示作成
- Claude Codeの結果レビュー
- GitHub上の正式記録の読み込み
- 次の判断材料の提示

ChatGPTは、実際に実行していない操作を実行済みとは表現しない。

ChatGPTは、GitHub連携が利用可能な場合、引き継ぎファイル等の正式記録をGitHubから直接読み込んで新しいチャットを再開できる。

## C. Claude Codeの責任範囲
Claude CodeはWindows上で、
- ファイルの作成・編集
- リポジトリ確認
- Git status / diff
- 実装
- commit
- push
等を実行できる。

ただし、Claude Codeは「引き継ぎそのもの」に必須ではない。
通常のチャット引き継ぎでは、ChatGPTがGitHub上の正式な引き継ぎファイルを直接読み込めるため、GPT → Claude Code → 引き継ぎファイル → 新GPTという中継を必須としない。

Claude Codeは主として、
- コード・ファイルの実装
- ローカルリポジトリの確認
- Git操作
- 実装結果の検証
を担当する。

commit / push / 公開 / 本番反映など重要操作は、人間の明示的承認を受けてから行う。

## D. 標準的な実行フロー
### D-1. 通常の作業
1. ChatGPTが目的と範囲を整理する。
2. 必要に応じてClaude Codeへ実装指示を作成する。
3. Claude Codeが実装・確認する。
4. Claude Codeが結果・変更ファイル・git status等を報告する。
5. ChatGPTがレビューする。
6. 人間が重要操作を承認する。
7. commit / push等を実行する。
8. GitHub側の反映を確認する。

### D-2. チャットを新しくする場合
1. 現在のChatGPTチャットで、現在状態・決定事項・未決事項・次の作業を整理する。
2. 必要な正式情報をGitHub上の引き継ぎファイルへ反映する。
3. 重要なGitHub変更は人間が確認・承認する。
4. 新しいChatGPTチャットを作成する。
5. 新しいチャットからGitHubの引き継ぎファイルを直接読み込む。
6. 引き継ぎ内容とGitHub上の実状態に差異がないか確認する。
7. 確認後、作業を再開する。
8. 旧チャットは原則として「【過去版】」にリネームする。

### D-3. PC・スマートフォン共通運用
- PCとスマートフォンのどちらからでも、GitHubを正式記録として同じ引き継ぎ情報を参照する。
- 引き継ぎ目的で、PCからファイルをダウンロードしてスマートフォンへ移送することを原則として行わない。
- 新しいチャットからGitHub上の正式記録を直接読み込む方式を基本とする。
- 通常の作業資料（画像、PDF等）のアップロードが必要な場合は、その用途に応じて別途扱う。

## E. 引き継ぎファイルの考え方
引き継ぎ情報は、可能な限り以下のように分離する。
- CLAUDE.md：プロジェクトAIの基本憲章・作業規則
- STATUS.md：現在の実装状態
- PROJECT.md：プロジェクト概要
- DECISIONS.md：重要な意思決定
- ISSUES.md：未解決事項
- HANDOFF.md：直近の引き継ぎ

AI戦略司令室では、当面以下の専用ファイルを正式な引き継ぎ記録として使用する。
- AI戦略司令室_引継ぎ_YYYYMMDD.md
- AI戦略司令室_運用ルール_YYYYMMDD.md

引き継ぎファイルは、チャット全文のコピーではなく、次のチャットが作業を再開するために必要な正式状態を簡潔に記録する。

## F. 引き継ぎ情報の整合性
- 引き継ぎファイルにGit HEADを記録する場合は、更新時に実際のGitHub上のHEADと照合する。
- Git HEAD、branch、commit、未commit変更等を記録する場合、確認していない情報を推測して記載しない。
- GitHubの実状態と引き継ぎファイルの記述が異なる場合、GitHubの実状態を優先し、その差異を次回更新時に修正する。
- 新しいChatGPTチャットでは、可能な限りGitHub上の実ファイルを直接読み込み、チャット履歴や記憶だけで正式状態を補完しない。

## G. チャットのライフサイクルと命名
- 現在作業中のチャットを「【最新版】」とする。
- 新しいチャットへの移行が完了した旧チャットは、原則として「【過去版】」にリネームする。
- 新しいチャットでGitHubから正式な引き継ぎファイルを読み込み、再開確認が完了するまでは、旧チャットを現役の基準として保持する。
- 不要なテスト用チャットは、正式記録がGitHubに保存されていることを確認したうえで、原則として削除より「【過去版】」へのリネームを優先する。
- ChatGPTのチャット一覧は作業セッションの一覧であり、正式なプロジェクト履歴そのものではない。

## H. トークン・ファイルアップロード抑制
- 過去チャット全文を新しいチャットへ持ち込むことを原則としない。
- 引き継ぎ時は、GitHub上の正式な引き継ぎ情報だけを読み込むことを基本とする。
- 引き継ぎ目的のファイルをChatGPTへ再アップロードする運用を原則として避ける。
- これにより、長大なチャット履歴の再処理、引き継ぎ用ファイルの再アップロード、アップロード上限や停止の影響を可能な範囲で抑制する。
- ただし、通常の資料・画像・PDF等のアップロード制限や、ChatGPTの利用上限そのものがなくなるわけではない。

## I. Git操作の安全ルール
- 既存の未commit変更を勝手に消さない。
- reset / restore / stash / discardを勝手に実行しない。
- 指定外ファイルを変更しない。
- commit前に変更対象を確認する。
- push前にcommit内容を確認する。
- push後はGitHub側で反映を確認する。
- 未commit変更がある場合、それを保護したまま作業できるかを事前確認する。
- merge / rebase等で既存の未commit変更に影響する可能性がある場合、先に人間へ報告する。
- force pushは原則として使用しない。

## J. 人間の承認
以下は人間の明示的承認を必要とする。
- 重要な設計変更
- 既存コードへの重要な変更
- commit
- push
- 公開
- 本番反映
- reset / restore / stash / discard
- force push
- 既存正式記録の削除・大幅変更

## K. 今回の運用方式の基本原則
AI戦略司令室の基本構成を以下とする。

ChatGPT ⇄ GitHub ⇄ ChatGPT

Claude Codeは必要な実装・ローカル作業・Git作業のときに参加する。

GitHubを長期的な正式記録、ChatGPTチャットを作業セッションとして扱うことで、チャットの長大化、引き継ぎ用ファイルの再アップロード、チャット乱立による混乱を可能な範囲で抑制する。

最終的な意思決定・重要操作の承認は人間が行う。

- 監視による調査・修正案の作成は自動化できるが、設問やリポジトリを自動で編集・commit・push・公開しない。変更は既存のレビューと人間承認の手順に従う。巡回に失敗した資料や未照合の設問は「未確認」として明示する。


## M. 全アプリ共通の教材検証基準（2026-10-03合意）
対象：ゼロナビ、ミチト、今後開発する全ての学習・試験対策アプリ。既存教材の改訂にも適用する。

1. 対象版・コミット・教材ファイルのハッシュ・全問題IDを固定する。公開版と候補版を区別する。
2. 全問について、設問の自然な日本語、前提条件、対象者・機体・場所・時点、原則と例外を確認する。
3. 正解だけでなく全ての誤答を個別に根拠照合し、誤りとなる理由を記録する。○×問題では、文全体の真偽と、誤りを正した文章を記録する。複数の解釈・複数正解・正解なしを排除する。
4. 計算は作成時の解説・正解を流用せず、設問の入力値から独立に再計算する。公式の適用条件、単位、境界値、丸め、近似・切り下げ、全選択肢まで確認する。
5. 根拠は現行の一次資料本文を確認し、資料名・URL・版・条項・確認日・施行日・適用範囲を記録する。教則・法令・標準マニュアル・個別許可条件・メーカー仕様を混同しない。既存の訂正履歴と運用ルールを先に読み、過去の結論を変える際は差分の根拠を示す。
6. 解説は正解の理由・各誤答の理由・必要な条件や例外を説明し、設問・正解・根拠と矛盾しないことを確認する。
7. 教材品質は、知識以外の手掛かり（正解だけ長い、構文の違い、不自然な日本語、極端な誤答、正解位置の偏り）を点検する。文字数・キーワード検査は抽出に限定し、合格判定には使わない。誤答は関連知識の混同や実際に起こる誤解を用い、単なる文の水増しや不必要な難語は避ける。
8. 全体として、問題間の矛盾・重複・近似問題の偏り・出題範囲と難度の配分を確認する。公式サンプルとの比較と現行試験形式の確認を行う。旧サンプルを現行法令の根拠に使わない。
9. 修正後は内容・全選択肢・解説・根拠を同じ基準で再検証し、出題・採点・シャッフル・復習・保存再開・模試・履歴への反映を必要な範囲で確認する。教材検査とアプリ動作検査を区別する。
10. 問題IDごとに検証方法・結果・発見事項・修正前後・根拠・再検証結果・未確認事項を記録する。検証項目ごとに「確認済み／要修正／保留／未検証／対象外（理由付き）」を区別し、対象外を合格件数に混ぜない。
11. 機械検査の合格、一部の本文照合、全問を読んだことを「全問検証完了」と表現しない。独立した第三者レビュー・受験者による難度と学習効果の評価は別項目として記録し、未実施を明示する。追加AIレビューも根拠確認の代替にはしない。
12. 公開判断には、各必須項目の対象数・確認済み数・未確認数と、重大な未解決事項を提示する。重大な正誤・根拠・採点の疑義を残したままリリース可としない。合格実績がない段階で合格を保証しない。

この追記は教材検証ルールの変更承認であり、公開アプリの教材変更・配信承認ではない。既存の公開承認手順を維持する。停止済み定期ルーティンは再開しない。

## N. 三者AIによる教材検証（2026-10-04正式登録）
対象：ミチト、ゼロナビ、今後の試験対策アプリ。M章の教材検証基準に追加適用する。
- 今回の20問で、正答一致だけでは見えない未確認根拠・文章上の課題を比較できたため、GPT・Claude・Geminiの三者レビューを正式な補助検証プロセスとする。20問の成功を全問品質・学習効果の証明としない。
- 対象コミット・候補ハッシュ・問題ID・資料版を固定する。GPTが作成／一次検査、Claude・Geminiが別系統の内容査読、GPTが根拠再照合と比較台帳統合を担当する。作成者GPTの自己検査と、完全に独立した第三者査読を混同しない。
- Phase A：候補キー・解説と他AIの今回結果を伏せ、設問と全選択肢から判定する。既存訂正履歴を渡した場合は完全盲検とは呼ばない。各AIが自分の判定を保存する。
- Phase B：各AIに自身のPhase A記録と候補キー・解説を渡して照合する。他AIの今回判定は照合終了まで渡さない。Phase Aを上書きせず、変更理由を記録する。
- 多数決・全員一致・AIのreviewed／source_verified自己申告を合格条件にしない。相違点と未確認事項は一次資料の本文・適用条件で解決する。AIの指摘も誤り得るため、根拠のない修正を採用しない。
- 根拠本文または利用条件に応じた該当抜粋・取得ログ、資料名、URL、法令ID、改正版ID、取得日時、本文ハッシュ、条項、施行日、適用範囲を記録する。ツール呼出しだけで本文確認済みとしない。該当項の定義・括弧書き・例外を含め、要約や抜粋漏れは全文で再確認する。
- 別プロセスのPhase Bに根拠を引き継ぐ場合は固定済み本文・証跡を渡すか再取得する。Phase Aの自己申告JSONだけでは本文の再確認完了としない。
- CLI版、要求モデル、実際のモデル（取得可能な場合）、日時、入力ハッシュ、未加工応答、正規化結果、検証器の格下げ理由を保存する。復元結果は元の実行日時・候補ハッシュと復元日時を分け、再実行と呼ばない。
- 各問題×検査項目の台帳をGitで管理する。設問、全選択肢、正答、解説、文法・手掛かり、重複・網羅性、根拠・施行日、人間専門家査読、実学習者試行、アプリ動作、公開判断を別欄にする。確認済み／要修正／保留／未検証／対象外（理由付き）を区別し、変更前後・理由・担当・再検証・参照commitを追記する。
- 全問への適用を目標とし、実施は固定したバッチ単位で進める。優先20問は目的選定であり代表標本ではない。法改正は資料と問題IDの対応から全問の影響を調べ、変更した設問・選択肢・キー・解説を再査読する。
- 三者AI検証は人間専門家査読・実学習者試行を置換しない。重大な正誤・出典・採点の未解決事項を残したリリースは承認しない。公開承認、本人認証、実機受入は既存の人間担当を維持する。
- PowerShellからClaude／Geminiを自動起動し、最小権限・隔離した出力先で記録する。認証失敗・取得失敗を合格にしない。定期処理の再開やアプリ教材の自動公開は含まない。

## O. PowerShellの単一REPORTとSTART／END（2026-10-04統合）
- 過去経緯：10月2日のAPP-VERSION-MANAGEMENT-20261002.mdにSTART／ENDの既決規定と適用漏れが記録済み。同日12:42の追記で「手動共有が必要なときのみ、最後に単一REPORT、Claudeは本文だけ」へ更新された。今回の実行ファイルへの反映漏れを是正し、この章を出力規定の現行基準とする。
- 人間へ共有するPowerShell結果は、最後に単一の区切り付きREPORTを表示・UTF-8保存する。進行中のログと最終REPORTを区別する。ユーザーはSTARTからENDまで両行を含めてコピーする。
